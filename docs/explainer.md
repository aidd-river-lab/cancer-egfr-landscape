这份文档假设你：会写代码、懂 REST API、懂数据库、没有生物/化学背景。所有生物概念都会先给一个编程类比，再讲学术定义。这是遵循项目 prompt 文档里定的规矩："涉及生物/化学概念，先用简明语言配合编程类比讲清楚原理"。

## 0. 一句话概括

我们在查一个具体问题："肺癌病人身上最常见的一种耐药突变（19del），现在公开的药物设计数据库里完全没有对应的'药物结构'可以参考——我们能不能用计算的方法，给它猜一个可能的候选方案？"

答案：猜出了一个（对接出一个奥希替尼跟这个突变体结合的姿势，打分 -7.357 kcal/mol），但这只是一个**计算假说**，不是结论，不能吃、不能用来治病，需要真实实验验证。

## 1. 背景故事：EGFR 和癌症耐药

### 1.1 基因、蛋白质、突变——用代码类比

- **基因** ≈ 源代码。一段 DNA 序列，"写"着怎么造一个蛋白质。
- **蛋白质** ≈ 编译 + 运行后的程序实例。基因这段"源码"被细胞里的机器"编译"（转录+翻译）成一条氨基酸链，这条链会自己折叠成一个特定的 3D 形状，这个形状决定了它的功能——就像同一份源码编译出的二进制文件，是一个可以被调用、有具体行为的"运行时对象"。
- **突变** ≈ 打了一个补丁（patch），改了源码里一两行。可能是良性的（不影响行为，等价于改了个注释），也可能是致命的（改坏了一个关键的 if 判断，程序从此行为异常）。

### 1.2 EGFR 是什么，为什么它的突变会致癌

EGFR（表皮生长因子受体）是一种蛋白质，长在细胞膜上，功能类似一个**事件监听器**：

- 平时处于"睡眠"状态，不做事。
- 细胞外面出现特定的信号分子（配体）时，触发它，它就会发出"开始增殖"的信号（对应到细胞内部一连串的分子事件，最终结果是"这个细胞该分裂了"）。
- 正常情况下这个监听器受严格控制：没信号不触发，触发一次就归位，等下一次信号。

EGFR 的致癌突变（比如项目里反复出现的 L858R、19号外显子缺失）干的事情，用代码类比就是：**把这个事件监听器的判断逻辑改坏了，变成了一个死循环——不需要外部信号，它自己就一直触发"开始增殖"这个事件**。细胞因此不受控制地疯狂分裂，这就是肿瘤形成的分子机制之一。

### 1.3 靶向药和耐药：一场军备竞赛

肺癌里如果测出 EGFR 有这类突变，医生会用**靶向药**——一种专门设计出来、能钻进这个蛋白质的某个"口袋"（结合位点）、把它焊死不让它触发的小分子。这个"口袋"在生物学里叫 **ATP 结合口袋**（EGFR 正常工作要用到 ATP，靶向药就是去抢占这个位置，类似往一个函数的必经调用路径上打一个断点，直接卡死它）。

这里有一场典型的"攻防军备竞赛"，跟安全领域的漏洞/补丁很像：

| 代际 | 药物 | 干的事 | 后来怎么被"绕过"的 |
|---|---|---|---|
| 一代 | 吉非替尼/厄洛替尼 | 可逆地占住口袋 | 出现 **T790M**"看门人"突变，口袋形状变了，药挤不进去了（类似攻击者改了函数签名，老的 exploit 打不进去了） |
| 二代 | 阿法替尼 | 改成"焊死"（共价不可逆结合） | 副作用太大（同时也焊死了正常细胞里没突变的 EGFR，误伤太多） |
| 三代 | 奥希替尼（osimertinib，本项目主角） | 更精准地共价结合到 **C797** 这个位置，选择性更好 | 出现 **C797S** 突变（那个残基本身被换掉了，共价结合的化学反应位点都没了——类似攻击者直接删掉了漏洞函数） |

本项目里反复出现的几个位点名字（L858R、T790M、C797S、19del）就是这场军备竞赛里，各个阶段冒出来的"新一版补丁"。**19del**（19号外显子缺失突变）是本项目最后聚焦的目标，它本身就是很常见的耐药相关突变，跟 L858R 是两个最主要的"入场券"式突变。

## 2. 什么是"PDB 结构"

科学家用 X 射线晶体学等实验手段，把一个蛋白质"拍"成一个精确的 3D 坐标文件——每个原子在空间里的 x/y/z 坐标。这个文件格式叫 **PDB**（Protein Data Bank），可以类比成：

- **一个内存快照 / 一份序列化的对象图**：蛋白质本来是活的、会动的，但晶体学拍出来的是它"定格"在某一个状态下的坐标快照。
- 全世界所有公开发表的这类"快照"都汇总在 **RCSB PDB** 这个公共数据库里，每个快照有一个 4 位的 ID（比如本项目用到的 `6LUD`、`7TVD`），可以理解成一个全局唯一的 commit hash。
- 一个"快照"里除了蛋白质本身的原子坐标，有时候还会带着一个**结合在它身上的小分子药物**的坐标——这种"蛋白质+药物"一起被拍下来的快照，叫**共晶结构（complex structure）**，是药物设计里最有价值的数据，因为它直接告诉你"这个药具体是怎么摆放在口袋里的"。

本项目大量用到的两个真实结构：
- **6LUD**：EGFR(L858R/T790M/C797S 三重突变体) + 奥希替尼 的共晶结构，能看到药物真实的结合姿态。
- **7TVD**：EGFR(19del 突变体) 的**裸结构（apo structure）**——只有蛋白质，没有任何药物结合在里面。这就是本项目找到的"结构空白"。

## 3. 模块一：查真实患者数据里，EGFR 到底哪些位点突变得最多

### 3.1 数据从哪来

**cBioPortal** 是一个公开的癌症基因组数据库，提供标准的 REST API（Swagger/OpenAPI 规范），背后是像 TCGA（癌症基因组图谱计划）这样的大型公开测序项目的数据。类比：它就是一个"癌症患者基因组数据"的公开只读 API，你可以像调用任何第三方 API 一样，用 Python 的 HTTP 客户端库去查。

我们用的具体队列叫 `luad_tcga_pan_can_atlas_2018`（LUAD = 肺腺癌，这个癌种里 EGFR 突变最常见），里面有几百个真实（已脱敏）病人的测序结果。

### 3.2 脚本做了什么（`01_clinical_data/fetch_egfr_mutations.py`）

1. 用 `bravado`（一个自动根据 Swagger 规范生成客户端调用方法的库，类似用 OpenAPI spec 自动生成的 SDK）连上 cBioPortal。
2. 查这个队列下，"哪个数据集是记录基因突变的"（叫 molecular profile），"哪份样本清单是包含全部测序过的病人"（叫 sample list）——**没有硬编码猜这两个 ID 的具体拼法，而是运行时动态查出来的**，因为不同队列的命名规则不完全一致，猜错了会拿到空数据却不报错，很危险。
3. 按 EGFR 这个基因（用 NCBI 的 Entrez Gene ID `1956` 定位，这是它在 NCBI 数据库里的"主键"）去查这个队列里所有病人身上，EGFR 上具体测到了什么突变。

**踩的坑**：用 bravado 生成的客户端调用时，明明 HTTP 响应是合法的 200 + JSON，但 bravado 自动把 JSON 反序列化成 Python 对象这一步却稳定返回 `None`（这是 bravado 处理 cBioPortal 这份规模较大的 API 规范时的已知兼容性问题）。解决办法：绕过它的反序列化层，直接读底层 HTTP 响应的原始 JSON 字符串自己解析——有点像发现某个 ORM 的自动映射不靠谱，干脆绕过 ORM 直接读原始 SQL 结果集。

### 3.3 结果怎么处理（`01_clinical_data/aggregate_mutation_frequency.py`）

原始数据里每条记录长这样：`proteinChange: "L858R"`，意思是"858号氨基酸从 L(亮氨酸) 变成了 R(精氨酸)"，这是描述蛋白质层面突变的标准记法（有点像 diff 的记法：`第858位: L -> R`）。

- 把描述"同一类事件"的不同写法归并成一类：比如 `E746_A750del`、`L747_P753delinsS` 这些不同的、跨越 19 号外显子区域的缺失突变，临床上统一叫 **19del**（类似把很多条具体的 git diff 归并成同一个"重构类型"打标签）。
- 按归并后的位点分组计数，算频率，排序。
- **不认识的格式不静默丢弃**：无法归并的记录单独计数并打印出来，方便人工检查——这是为了避免"看起来跑通了，其实丢了数据"这种静默错误。

### 3.4 真实结果

86 条真实突变记录里：

- **L858R：31.5%**（最常见）
- **19del：27.4%**（第二常见）
- 后面 T790M、G719A 等各占几个百分点，一堆只出现1次的（可能是罕见的、非驱动性的"乘客突变"）

## 4. 模块二：这些高频突变位点，有没有公开的"药物结构"可查

### 4.1 数据从哪来

**RCSB PDB** 除了能直接下载单个结构文件，还提供一个 **Search API**，可以像查搜索引擎一样，按关键词、按结构化字段去检索几十万个已发表的结构。

### 4.2 "结构覆盖"是什么意思（这个定义是跟你确认过的）

我们关心的不是"这个位点有没有被解出过结构"，而是更严格的："有没有一个结构，**既解出了这个突变位点，又同时解出了一个药物/抑制剂结合在里面**"。

为什么要这么严格？因为纯蛋白质结构（没有药物）对"设计新药"这件事帮助有限——真正有用的是"药物具体怎么摆放"这个姿态信息。这就像你说"这个 API 端点有没有文档"，光" 端点存在"不够，得"有带示例请求/响应的文档"才算真的有用。

### 4.3 踩的坑：全文检索不靠谱，会有假阳性

一开始用 RCSB 的全文检索（关键词搜索，类似 SQL 的 `LIKE '%xxx%'` 或 Elasticsearch 的模糊匹配），搜"EGFR 突变体名字"，发现**它会把根本不是 EGFR、而是同一家族的另外两个基因（BRAF、HER2）的结构也搜出来**——因为那些结构的标题里恰好也出现了相似的关键词（比如"kinase domain...deletion mutant"这种通用描述）。

这就跟你写了一个模糊搜索，返回结果里混进了不相关的记录一样。解决办法：**不能只信全文检索的结果，必须用结构化字段做二次核对**——具体是查每个候选结构的 `polymer_entity` 记录，看它挂的 UniProt ID 是不是真的是 EGFR 的 `P00533`（这是 EGFR 蛋白在 UniProt 数据库里的唯一编号，相当于一个跨数据库的外键）。这一步相当于"先用模糊搜索粗筛候选，再用精确的唯一键复核，排除误伤"。

同理还踩了一个坑：很多结构里"配体"列表里混着甘油、硫酸根这类**结晶时用的化学添加剂**，不是真正的药物——加了一份已知添加剂/离子的黑名单去过滤，才不会把"结构里随便混了点缓冲液成分"误判成"有药物结构覆盖"。

### 4.4 真实结果

- **L858R**：有覆盖，真实找到多个共晶结构（比如 7OXB、9XU9）
- **T790M**：有覆盖
- **19del**：**没有覆盖**——唯一搜到的匹配结构 `7TVD` 是裸结构（apo），没有任何药物结合在里面

这就是模块二找到的"结构空白"：**19del 是队列里第二高频的突变，但公开数据库里连一个"药物+19del蛋白"的共晶结构都没有**。

## 5. 模块三：分子对接——用算法猜一个可能的结合姿势

这是最"计算"、离生物学最远、离算法最近的一部分。

### 5.1 什么是分子对接（molecular docking）

用编程语言描述：**给定一个固定不动的大分子（受体，蛋白质）和一个可以自由旋转、平移、甚至改变自身构象（可旋转键的角度）的小分子（配体，药物）， 在一个限定的 3D 搜索空间里，用一个"打分函数"评估每一种摆放方式的"契合程度"（能量越低=契合越好），搜索出打分最好的几种摆放方式。**

这本质上是一个**局部优化搜索问题**，类比你熟悉的算法：
- 打分函数 ≈ 目标函数（loss function），越小越好（这里单位是 kcal/mol，代表一种"结合自由能"的估计，纯粹是打分函数算出来的相对值，不是真实测量值）。
- 搜索过程 ≈ 类似模拟退火/遗传算法的随机化局部搜索——不是穷举，是启发式地在解空间里跳来跳去找局部最优。
- **AutoDock Vina** 就是我们用的这个搜索算法的具体实现（一个开源的、业界常用的对接程序）。

### 5.2 准备工作：格式转换

Vina 不直接吃 PDB 文件，它要一种叫 **PDBQT** 的格式——在原始坐标基础上，额外标注了：每个原子的电荷（打分函数要用）、哪些键是可以自由旋转的（决定了搜索空间的自由度）。这一步类似"把一个通用的数据格式转换成某个特定工具要求的、带元数据的私有格式"，工具是 **meeko**（官方命令行工具 `mk_prepare_ligand.py` / `mk_prepare_receptor.py`，我们直接调用官方命令行，没有自己拼底层 API，减少出错概率）。

配体（奥希替尼）这边，先用 **RDKit**（一个化学信息学的 Python 库，可以理解成"处理分子结构的 Pandas/Numpy"）从它的 SMILES 表达式（一种用一行文本描述分子结构的记法，类似用正则表达式描述一个复杂的树形结构）生成一个具体的 3D 构象，再转 PDBQT。生成的分子式/分子量/LogP 跟已知的奥希替尼真实数据（C28H33N7O2, MW 499.62）完全吻合，说明这一步没出错。

### 5.3 定义搜索空间（docking box）

3D 空间无穷大，不可能全空间搜索（太慢，等价于没有剪枝的暴力搜索），得先框定一个大概的立方体区域（docking box：中心坐标 + 长宽高），只在这个盒子里搜。这个盒子通常根据"已知这个口袋大概在哪"来定。

**问题**：7TVD 是裸结构，没有药物，怎么知道口袋在哪？我们借用了 6LUD 里**真实的奥希替尼结合位置**来定位——反正 7TVD 和 6LUD 都是 EGFR 同一个激酶结构域，ATP 口袋的大概位置在结构上应该是保守的。

### 5.4 踩的大坑：两个 PDB 文件的坐标系是完全无关的

这是整个项目里最容易踩、也最容易被忽略的坑，用编程语言讲清楚：

> **6LUD 和 7TVD 是两次完全独立的实验解出来的结构文件。它们各自的 (x, y, z) 坐标建立在各自实验当时的、任意的参照系下**——就像两个不同数据库里各自的自增主键，数值上可能撞车，但完全不是同一个东西。

第一版实现犯的错：直接把 6LUD 里配体的坐标数字，当成 7TVD 坐标系下的框中心去用。程序**不会报错**（毕竟数字运算完全合法），但算出来的框会落在 7TVD 结构完全无关的空间位置——这是一种"运行时不报错，但结果是错的"的典型 bug，比直接崩溃更危险。

**修复方法：结构叠合（structural alignment）**，具体算法叫 **Kabsch 算法**：

1. 找两个结构里"编号相同的残基"（因为它们是同一个蛋白的不同突变体，大部分残基编号是对应的）。
2. 取这些残基里代表主链位置的 CA 原子坐标，在两个结构里各拿出一份。
3. 求一个刚体变换（旋转矩阵 R + 平移向量 t），使得"变换后的 6LUD 坐标"尽可能贴近"7TVD 坐标"——这是一个标准的最小二乘问题，用 SVD 分解求解（这部分代码在 `3_prepare_receptor.py` 的 `kabsch_fit` 函数，纯 numpy 实现，不到 20 行）。
4. 求出这个变换后，把 6LUD 里配体的坐标也做同样的变换，这样才是"配体在 7TVD 坐标系下、正确的等价位置"。

用了 282 个残基做这个拟合，拟合误差（RMSD）2.88 埃——这个数字可以理解成"两个结构叠在一起，平均每个原子差多远"，2.88 埃对两个不同突变体/不同晶体来说是合理范围。

**独立交叉验证**：光看这个 2.88 埃的数字还不够放心，所以又做了一次完全独立的验证——直接用 prompt 文档里给出的、这个口袋的关键残基编号列表（不依赖 6LUD，只用 7TVD 自己的坐标），算出这些残基的质心，跟叠合算出来的框中心比较。**两者只差 1.72 埃**（框本身有将近 20 埃见方）——两条独立的证据链吻合，才真正确认这个框定位对了。这跟写代码时"不能只信一个单元测试，最好再从另一个完全独立的角度验证一次"是一个道理。

### 5.5 装 Vina 踩的坑

- `pip install vina` 直接编译失败，报错缺 Boost C++ 库——这个 PyPI 包本身要从 C++ 源码编译。
- homebrew 也没有现成的 Vina 安装包。
- 最后用 **conda** 装成功：`conda create --override-channels -c conda-forge vina`，装的是预编译好的二进制，不用编译，几分钟搞定。`--override-channels` 是绕开 Anaconda 官方渠道最近加的一个"需要额外同意服务条款"的限制，只用不受影响的 conda-forge 渠道。
- 装好的 Vina 是 1.2.7 版本，命令行**没有** `--log` 参数（比某些教程里的旧版本用法少了这个选项）——改用 shell 的 `tee` 命令自己把输出存成日志文件。

### 5.6 阳性对照：先证明这套流程本身靠谱

这一步是整个模块三里最重要的"质量保证"环节，用编程语言讲：**在把这套流程用在一个"不知道答案"的新场景（7TVD）之前，先在一个"已经知道正确答案"的场景上跑一遍，看结果对不对**——这跟"先写一个能通过已知 case 的回归测试，再敢信任这段逻辑在新输入上的输出"是完全一样的思路。

具体做法：把奥希替尼对接回 **6LUD**（它真实结合在这里，我们知道真实的结合姿势长什么样），假装不知道答案，走一遍完整流程（用它自己的真实配体位置定义框——不涉及跨结构坐标变换，这一步排除了变量），看 Vina 自己搜出来的最佳姿势，跟真实晶体结构里的位置差多远。

**结果：只差 0.45 埃**（奥希替尼分子本身跨度接近 20 埃）。这说明：在这个已知案例上，Vina + 我们这套准备流程，确实能在完全不知道答案的情况下，自己搜出接近真实答案的姿势。这给了"7TVD 那边算出来的结果多少有点参考价值"多一分底气——但请注意，这**不是数学证明**，只是"在一个已知案例上表现良好"的经验记录，不能保证对所有新场景都同样准。

### 5.7 对 19del（7TVD）的真实探索性结果

对接出 9 个候选姿势，按打分排序，**最佳姿势 affinity = -7.357 kcal/mol**（同样条件下，阳性对照 6LUD 那边是 -8.192 kcal/mol，可以作为一个数量级上的参照）。

**这个数字到底意味着什么，不意味着什么**：

- 意味着：在这一次计算、这一套参数下，Vina 认为这是它搜到的、契合度打分最好的一种摆放方式。
- **不意味着**：这个药真的能结合到这个突变体上、这个突变体"有药可治"、这个数字可以跟其他任何论文/软件算出来的数字直接比较。打分函数是一种粗糙的经验公式，不是真实的物理测量。真正要确认"能不能结合"，需要湿实验（比如做一个体外的结合实验，测真实的解离常数）。

用一条链路串起来：

```
真实患者数据(cBioPortal)
   └─▶ EGFR 最常突变的两个位点: L858R(31.5%), 19del(27.4%)
          └─▶ 查公开结构库(RCSB PDB): L858R 有药物结构, 19del 没有
                 └─▶ 19del 是"结构空白" —— 针对它做探索性计算对接
                        ├─▶ 先做阳性对照: 流程本身可靠(误差0.45埃)

```

这是一个完整的、从真实数据出发、每一步都有真实验证（不是拍脑袋编数字）的计算流程。它的价值在于**方法论本身**——怎么正确地把临床数据、结构数据库、计算对接这三类完全不同的资源串起来，并且在每一步都留了"怎么验证这一步没做错"的手段（交叉验证、阳性对照）。
