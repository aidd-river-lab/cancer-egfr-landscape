# 方法说明

> 这份文档假设你已经有基本的生物/化学背景知识。如果你是程序员、没有这个背景，先看 [`explainer.md`](explainer.md)——每个概念都配了编程类比。

## 1. 临床突变频率（`01_clinical_data/`）

### 数据来源

- **队列**：`luad_tcga_pan_can_atlas_2018`（TCGA 肺腺癌，PanCancer Atlas 版本），通过 cBioPortal REST API v3 获取。
- **基因**：EGFR（Entrez Gene ID `1956`）。
- **客户端**：`bravado.client.SwaggerClient`，从 `https://www.cbioportal.org/api/v3/api-docs` 加载 Swagger/OpenAPI 规范。
- **拉取范围**：脚本运行时**动态查询**该 study 下类型为 `MUTATION_EXTENDED` 的 molecular profile、以及名称含 "all"（全部有测序数据的样本）的 sample list，再据此拉取 EGFR 的突变记录——不硬编码猜测的 profile id / sample list id 字符串，避免因 ID 命名规则变化而静默拿到空数据或错误数据。

### 聚合方法（`aggregate_mutation_frequency.py`）

1. 从原始突变记录里取 `proteinChange` 字段（cBioPortal 标准字段，形如 `L858R`、`T790M`、`E746_A750del`）。
2. **位点归一化**：把描述同一类事件的不同写法合并到同一个标签下，规则：
   - 19号外显子附近的各种缺失变体（`E746_A750del` 等一系列跨越19号外显子的 in-frame deletion）统一归并为 `19del`——这是临床文献里通用的做法，因为它们的耐药机制/靶向药响应模式高度相似，逐个亚型拆开对"哪些位点值得做结构覆盖分析"这个问题没有额外信息量。
   - 单点错义突变（`L858R`、`T790M`、`C797S`、`G719S` 等）保留原始蛋白质变化记法。
   - 无法归一化（缺失 `proteinChange`、或格式不认识）的记录单独计数，不静默丢弃，输出时会在日志里报告"跳过了多少条、什么原因"。
3. 按归一化后的位点分组计数，计算频率 = 该位点计数 / 总突变记录数（分母不含无法归一化的记录）。
4. 按频率降序排序输出。

### 已知局限性

1. **队列代表性有限**：TCGA PanCancer Atlas 是一个特定的回顾性测序队列（美国为主的样本构成），EGFR 突变率和位点分布在东亚人群 vs 欧美人群中已知有显著差异（东亚非吸烟肺腺癌患者 EGFR 突变率明显更高）。本仓库默认队列的频率排序**不能**直接当作"全球/中国患者的真实分布"。
2. **位点归一化会掩盖亚型差异**：把 19号外显子的多种缺失变体合并成 `19del`，简化了下游"结构覆盖"比对的复杂度，但也丢失了不同缺失亚型之间可能存在的、真实的耐药机制/结构差异信息。
3. **"未见于该队列" ≠ "临床罕见"**：位点在这个队列里频率低或没出现，可能只是这一批测序样本没覆盖到，不代表该突变在更大人群里真的罕见。
4. **突变记录 ≠ 功能验证**：cBioPortal 里的突变记录是测序检出的体细胞突变，本身不代表这个突变一定具有致病性/耐药功能——功能注释需要额外交叉比对（如 OncoKB、CIViC），本项目目前没有做这一层过滤。

## 2. 结构覆盖比对（`02_structure_mapping/`，进行中）

### "结构覆盖"的定义（已与项目作者确认）

一个突变位点被认为"有结构覆盖"，**必须同时满足**：

1. RCSB PDB 中存在解析出该突变位点的 EGFR 结构，**并且**
2. 该结构里同时解析了一个抑制剂/配体的结合复合物（即结构里除了蛋白链，还有一个与结合口袋有相互作用的小分子配体，且该复合物是被明确解析的，不是共结晶但未建模的杂质分子）

只满足条件1（比如只有 apo 结构，没有配体）**不算**覆盖——因为本项目的下游用途是给"结构空白位点的对接验证"（`03_docking_validation/`）提供候选起始构象，没有已知配体结合姿态的纯蛋白结构对这个目的帮助有限（虽然理论上仍可以用来做全新的对接，但那已经是"结构空白"场景该做的事，不应该被计入"已覆盖"）。

### 实现方式（实测确认，不是凭训练记忆编造的 API 用法）

1. 先用 RCSB Search API（`POST /rcsbsearch/v2/query`，`full_text` 服务）按 `"EGFR" + 位点记法` 粗筛候选 PDB。**实测发现单靠全文检索精度不够**——比如搜"EGFR deletion mutant kinase"会把 BRAF、HER2 的结构也搜出来（它们标题里同样有"kinase domain...deletion mutant"字样）。
2. 每个候选再用 RCSB Data API（`GET /rest/v1/core/...`）取权威结构化字段做复核：
   - 该结构的 polymer entity 是否真的挂着 EGFR 的 UniProt accession `P00533`（排除同源基因假阳性）
   - 标题里是否真的出现这个位点的记法
   - `nonpolymer_entity` 的 `comp_id` 是否命中已知的结晶添加剂/离子黑名单（甘油 GOL、硫酸根 SO4、PEG 等——这些会被误判成"有配体"，实际只是结晶缓冲液成分）
3. `19del` 没有统一的检索记法，退化成搜索标题含 "exon 19" 字样——这比单点替换突变的匹配弱很多，找到的候选数量本身就少，是这个类别覆盖判定精度较低的已知弱点。

### 已知局限性

1. 判定依赖 RCSB PDB 现有**已公开**结构的完整性——某个位点在 PDB 上没有抑制剂共晶结构，不代表业界真的没做过（可能有未公开、专利保护、或还没结晶成功的工作），这里的"结构空白"只是"公开数据里的空白"。
2. 结构覆盖的判定目前不区分抑制剂的"代际"（一代/二代/三代靶向药），一个位点即使只被某个已经临床淘汰的老药共晶覆盖过，也会被记为"有覆盖"——这对下游对接验证候选优先级排序是有影响的，后续可能需要加一层"覆盖它的抑制剂是否还有临床相关性"的过滤。
3. "结晶添加剂黑名单"是一份人工维护的已知常见添加剂/离子列表，不是权威的、PDB 官方维护的分类——理论上可能漏掉某个没见过的添加剂化合物代码，把它误判为"真配体"。
4. 位点匹配是"标题字符串是否包含该记法"，比结构化的突变字段匹配弱——如果某个结构的标题没有用标准记法描述突变（比如用了别的编号系统、或者突变信息只写在正文摘要而不在标题里），会被漏判为"没有覆盖"，属于假阴性风险。
5. 默认只处理频率表里 `count>=2` 的位点，跳过只出现1次的位点（这批真实数据里有19个这样的位点）——权衡是"这些很可能是罕见的乘客突变，逐个查 PDB 性价比低"，但也可能漏掉某个真实存在、只是这个小队列里恰好只测到1次的耐药位点。`--min-count 0` 可以强制跑全量。

## 3. 对接验证（`03_docking_validation/`）

针对模块2判定出的"结构空白"位点(目前是 19del，对应 apo 结构 7TVD)，尝试把奥希替尼对接进这个受体，产出**仅供参考的计算假说**——**不代表这个分子真的能结合 19del 突变体，也不代表这个位点"可成药"**，对接打分函数的估计误差本来就比较大，任何结论都需要湿实验（比如 SPR/ITC 结合实验）验证。

`target-egfr-c797s` 仓库在本地环境里没有找到，没能直接复用它已经跑通的 Vina 流程，改为按同样的思路独立实现。

### 流程与踩过的坑

1. **受体**：7TVD 是 apo 结构（没有配体），无法像正常对接那样"从已知配体位置定义搜索框"。用 6LUD（EGFR L858R/T790M/C797S + osimertinib 共晶结构）里配体的位置做参考。
2. **坑：两个 PDB 结构的坐标系是无关的。** 6LUD 和 7TVD 是两次独立的晶体学实验解出来的结构，各自的原子坐标建立在各自晶胞的任意坐标系下——第一版实现直接把 6LUD 里配体的 xyz 坐标当成 7TVD 坐标系下的框中心用，算出来的框位置明显不在 7TVD 结构附近。修复方法：用两个结构里残基编号相同的 CA 原子做最小二乘刚体叠合（Kabsch 算法），求出从 6LUD 坐标系到 7TVD 坐标系的旋转+平移变换，再把配体坐标变换过去。
3. **叠合质量**：用了 282 个公共残基，RMSD 2.88 埃（对同一激酶结构域的两个不同突变体/晶体形式来说是合理范围，但不算"完美吻合"）。
4. **独立交叉验证**：不只看 RMSD 数字，另外用 prompt 文档给出的、独立于 6LUD 的结合口袋残基列表（PDB 原始 SITE 记录），直接在 7TVD 自己坐标系下算这些残基的质心，跟叠合算出来的框中心比较——两者只差 1.72 埃（框本身有 17~24 埃见方），说明叠合定位到的确实是 ATP 口袋区域，不是叠合误差的巧合。
5. **配体制备**：用 RDKit 从 SMILES 生成奥希替尼的 3D 构象（`AllChem.EmbedMolecule` + MMFF 力场优化），算出来的分子式/分子量/LogP（C28H33N7O2, MW 499.62, LogP 4.51）跟 prompt 文档里已验证过的数值完全一致。
6. **PDBQT 转换**：用 meeko 官方命令行工具（`mk_prepare_ligand.py` / `mk_prepare_receptor.py`），没有自己拼底层 API——meeko 内部依赖链条比较长（额外需要 scipy、gemmi，装的时候是一路缺依赖一路补上的）。
7. **坑：Vina 装不上**——`pip install vina` 因为找不到 Boost C++ 库编译直接失败，homebrew 也没有现成的 autodock-vina 配方。改用 `conda create --override-channels -c conda-forge vina` 装到一个独立的 conda 环境，是预编译好的 1.2.7 版本，不用编译，跑起来了（`--override-channels` 是为了绕开 Anaconda defaults 渠道新加的服务条款确认，只用 conda-forge 这一个不受影响的渠道）。
8. **坑：Vina 1.2.7 的命令行没有 `--log` 参数**——比一些教程/旧版本用法少了这个选项，改成用 `tee` 自己把 stdout 存成日志文件。
9. **坑：6LUD 做自对接受体准备时，meeko 的残基模板匹配失败**——报错列出20多个残基"侧链原子缺失、匹配不上标准氨基酸模板"（常见于晶体结构里电子密度弱、侧链没能完全解出来的柔性区域），加 `-a/--allow_bad_res` 让 meeko 自动删掉这些残基后解决——这是 meeko 报错信息里自己给的推荐做法，不是猜的。
10. **阳性对照（self-docking control）已经补上**：把 osimertinib 对接回它真实结合的 6LUD 结构（用 6LUD 自己的真实配体位置定义搜索框，不涉及跨结构坐标变换），得到的最佳姿势跟晶体结构里的真实配体位置质心只差 **0.45 埃**（对比奥希替尼分子本身跨度接近20埃），说明这套准备+对接流程在这个已知阳性案例上表现良好，这给了"7TVD那边的探索性结果值得看一眼"多一点依据——但正如免责声明所说，这不是数学保证，只是一个已知案例上的表现记录。
11. **对 7TVD(19del) 的实际探索性对接结果**：最佳姿势 affinity = **-7.357 kcal/mol**（阳性对照 6LUD 那边是 -8.196 kcal/mol，作为数量级参照）——这只是一个计算假说，不是"能结合"的证据，需要湿实验验证。

### 已知局限性

1. **用 6LUD 的口袋位置给 7TVD 定框，依赖"两个结构的 ATP 口袋位置高度保守"这个假设**——已经用独立的口袋残基列表做过交叉验证（1.72埃），也补了阳性对照（0.45埃），但没有用 PyMOL 做过更细致的目视结构叠合检查。
2. **Vina 的 affinity 分数是打分函数的估计值，不是实验测量的结合自由能**，不同对接软件之间的分数不能直接比较，数值本身的绝对大小意义有限。7TVD 的 -7.357 kcal/mol 比阳性对照 6LUD 的 -8.196 kcal/mol 弱一些，但两个数字之间的差距本身能不能说明"19del对osimertinib的亲和力更低"，还是仅仅反映了apo受体构象/局部残基缺失的影响，不看更多对照没法下结论。
3. **阳性对照只验证了"姿势位置对不对"，没有验证"打分数值本身有没有意义"**——比如没有做"随机分子对接进同一个口袋、看打分是不是明显更差"这类阴性对照，所以 -7.357 kcal/mol 这个数字本身够不够"好"、算不算有意义的结合信号，还缺一层参照。
4. **只对接了 osimertinib 一个分子**——没有对比其他候选分子（比如一代/二代药）在同一个 19del 受体上的打分做横向比较，样本量是1，任何"osimertinib对19del可能怎样"的表述都要非常谨慎。
